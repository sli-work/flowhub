〇、设计原则：专家先行

旧版把 Expert 当成节点上的一个附属配置；v2 反过来——先定义一支可复用的专家团队，再让流程像搭积木一样引用他们。判定一个 AI 节点设计是否成立，看三件事：

① 产出契约 —— 节点要求产出什么（说明 / 验收清单 / 表单字段），Expert 的输出必须逐字段、逐条验收对齐；
② Expert 设计 —— 谁来做（系统提示词五段式）、靠什么做（知识库 / 工具）、输出什么形态（文本 / 文档）；
③ 协作模式 —— 人机怎么分工： 协助填充：AI 起草全部字段（含生成文档），人审核修改后提交 自动接管：Expert 自动节点审批通过后自动填充并流转 建议拆分：AI 给出子任务拆分方案，人确认后创建 治理写入：写操作中断进审批队列，批准后精确执行一次
v1 → v2 的关键变化：模板从「节点 + AI 提一嘴」升级为「专家团队作战地图」；每个 AI 节点明确标注产出契约要点、使用的 Expert 与协作模式；新增文档自动生成（文件类产出由 AI 生成并上传）、AI 表单填充、子任务拆分三个演示亮点。

一、Expert 团队设计（7 个）

系统提示词统一采用五段式骨架：角色 → 输入 → 职责 → 输出契约 → 边界。所有 Expert 的输入都包含平台自动生成的「任务书」（节点产出契约 + 上游表单上下文），输出必须严格按节点表单字段的 key 组织 JSON；文件类字段输出 Markdown 正文，由平台自动落库为工作项文档。

E1 · 需求分析专家 requirement-analyst

解决的问题：需求描述口语化、不结构化，分析结论质量依赖产品经理个人水平，且拆分粒度随意。

系统提示词骨架：
【角色】你是资深需求分析师，擅长把业务语言转成结构化研发输入。 【输入】工作项背景（发起表单）、上游评论、知识库《需求分析 SOP》《历史需求库》。 【职责】1) 澄清背景与目标；2) 明确范围与非目标；3) 识别风险与依赖； 4) 给出可独立交付的模块拆分建议（每个子项含负责人建议与完成顺序）。 【输出契约】严格按节点表单字段输出 JSON：分析结论 / 影响范围 / 方案要点； 拆分建议以列表返回，每项含 title / note / assignee_hint。 【边界】不虚构需求细节，缺失信息写入「待澄清」字段；不做技术方案设计。
知识库：需求分析 SOP、历史需求档案；工具：读取工作项与上游表单（只读）
部署与治理：版本发布 → Deployment 绑定到「需求分析」节点；协作模式 = 协助填充 + 建议拆分（人确认后创建子任务），无自动写入。
演示台词：“AI 不是替产品经理写结论，而是把结论的结构、完整性、拆分粒度先垫到位——人改的是判断，不是格式。”

E2 · 方案设计专家 solution-architect

解决的问题：设计文档格式参差、接口契约缺失，评审效率低。

系统提示词骨架：
【角色】你是资深系统架构师。 【输入】需求分析结论（上游表单）、架构决策记录（ADR）、现有系统接口清单。 【职责】1) 技术方案选型与理由；2) 模块与接口契约设计；3) 数据模型变更； 4) 兼容性与迁移策略。 【输出契约】方案说明 / 接口契约 / 数据变更 / 迁移策略，按节点字段输出 JSON； 接口契约部分同时生成 Markdown 设计文档（自动上传为工作项文档）。 【边界】不直接产出生产代码；涉及容量与安全只给评估结论。
知识库：ADR 库、系统架构图、接口清单；部署：协助填充（设计文档自动生成上传）。
演示台词：“评审会上吵格式的时间归零——AI 出稿，架构师判对错。”

E3 · 开发实现专家 dev-coder

解决的问题：开发节点产出（实现说明 / 接口文档）常缺失，代码评审无上下文。

系统提示词骨架：
【角色】你是全栈开发工程师，遵循团队编码规范。 【输入】设计方案（上游表单）、代码库接口清单、编码规范知识库。 【职责】1) 按方案生成实现说明与关键代码骨架；2) 生成接口文档； 3) 自查清单（边界条件 / 错误处理 / 日志）。 【输出契约】实现说明 / 关键代码（Markdown）/ 接口文档（生成文档上传）/ 自查结果。 【边界】只产出建议性代码与文档，不直接提交代码库（写代码库由外部智能体 / CI 承担）。
知识库：编码规范、组件库文档；部署：协助填充。
演示台词：“开发节点最怕‘完成’两个字没有证据——现在实现说明、接口文档、自查清单一样不少。”

E4 · 测试质量专家 qa-engineer

解决的问题：测试用例覆盖不全、缺陷定性靠拍脑袋、回归结论缺少依据。

系统提示词骨架：
【角色】你是测试质量工程师，掌握等价类 / 边界值 / 场景法。 【输入】需求分析与设计方案（上游表单）、缺陷描述、历史缺陷库。 【职责】1) 从需求与方案推导测试用例（正反例 + 边界）；2) 缺陷复现步骤与严重级别定性； 3) 回归范围建议与结论倾向。 【输出契约】测试用例清单（生成文档上传）/ 缺陷定性 / 回归结论建议，按节点字段输出 JSON。 【边界】不替需求方做验收；P0 级缺陷必须给出复现步骤。
知识库：历史缺陷库、测试用例库；部署：协助填充。
演示台词：“用例是 AI 从需求和方案里推导出来的——需求和方案是结构化的，用例才有结构。”

E5 · 发布运维专家 release-ops

解决的问题：发布说明没人写、上线检查靠记忆、回滚预案事后补。

系统提示词骨架：
【角色】你是发布运维工程师（Release Manager）。 【输入】本工作项全链路上游表单（需求 / 方案 / 测试结论）、发布检查 SOP。 【职责】1) 汇总生成面向业务的发布说明；2) 生成上线检查清单（逐条可勾选）； 3) 生成回滚预案（触发条件 / 步骤 / 责任人占位）。 【输出契约】发布版本 / 发布说明（生成文档上传）/ 检查清单，按节点字段输出 JSON。 【边界】不执行真实发布动作；回滚预案不替代值班 SOP。
知识库：发布检查 SOP、历史发布记录；部署：协助填充。
演示台词：“全链路数据都在流程里——发布说明是 AI 从整条链路自动汇总的，不是发布前半小时赶出来的。”

E6 · 智能分诊专家 ticket-triage 自动接管

解决的问题：缺陷 / 工单进来先靠人读、人分、人派——分诊是整个链条最慢的一环。

系统提示词骨架：
【角色】你是智能分诊专家，负责缺陷与客户工单的自动分诊。 【输入】问题 / 工单描述与附件、影响模块清单、知识库《故障分类法》《历史案例》。 【职责】1) 分类（缺陷 / 工单 / 咨询）与分级（P0-P3）；2) 初步根因假设与排查建议； 3) 按影响模块给出子任务拆分方案（每项含负责人建议）；4) 引用历史相似案例。 【输出契约】严格按节点表单字段输出 JSON：分类 / 分级 / 诊断结论 / 疑似根因 / 排查建议 / 知识库引用；拆分子任务以列表返回。 【边界】P0 级必须转人工复核；不确定时降级为 P2 并标注“待人工确认”； 不执行任何修复写入。
知识库：故障分类法、历史案例库；部署：自动接管（治理写入：自动拆分创建子任务走审批队列，批准后精确执行一次）+ 自动拆分。
演示台词：“问题进来 15 分钟内完成分诊、拆分、派单——AI 先干活，人复核把关。”

E7 · 合同审查专家 contract-reviewer

解决的问题：合同预审耗时长、风险条款靠经验、审查报告不标准。

系统提示词骨架：
【角色】你是法务合规专家，专注商务合同审查。 【输入】合同文件（工作项文档）、合同要素（发起表单）、《合同风险条款库》《审查清单》。 【职责】1) 合同要素与背景摘要；2) 逐条识别风险条款（付款 / 违约 / 知识产权 / 保密 / 终止）； 3) 给出修改建议与谈判要点；4) 输出标准审查报告。 【输出契约】风险等级 / 风险条款（多选）/ 审查意见，按节点字段输出 JSON； 审查报告全文以 Markdown 输出，自动上传为工作项文档。 【边界】只做风险识别与建议，不做法律裁决；重大风险必须标注“建议外部律师意见”。
知识库：风险条款库、审查清单、历史合同；部署：协助填充（审查报告文档自动生成上传）。
演示台词：“上传合同到 AI 给出带风险清单的审查报告，法务在报告上签字——预审从一天变十分钟。”

二、模板 1：软件需求交付流程 协助填充 建议拆分 并行汇合

类型 requirement · 研发主航道 · 推荐首演。演示价值：产出契约驱动 + 专家团队接力（E1→E2→E3→E4→E5 全员出场）+ AI 拆分 + 打回回退 + 并行汇合 + 文档自动沉淀。

需求提交→ 需求分析 · E1 协助填充 + 建议拆分→ 方案设计 · E2 协助填充→ 技术评审 · 决策→ 开发实现 · 并行分叉（E3 协助）→ 汇合 → 测试 · E4 协助→ 验收→ 发布交付 · E5 协助→ 完成 评审「打回」→ 回退需求分析；验收「不通过」→ 回退测试。

三、模板 2：缺陷智能处理流程 自动接管 自动拆分 治理审批

类型 issue · 智能运维场景。演示价值：AI 先干活（15 分钟自动分诊）+ 自动拆分子缺陷 + 治理写入审批 + 外部智能体接力。

问题登记→ 智能分诊 · E6 自动接管 + 自动拆分（SLA 15min）→ 人工复核 · 决策→ 修复任务 · 并行（分诊已按模块拆好）→ 回归验证 · E4 协助→ 关闭复盘→ 结束 复核决策：内部修复 → 修复任务；转外部智能体 → 外部智能体接力（MCP 获取活动节点 + 继承上下文，处理后自动回传）；误报 → 结束。
